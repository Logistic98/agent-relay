## 运行手册与故障排查

## 健康与验收

```bash
$ agent-relay doctor
$ curl -fsS http://127.0.0.1:8787/health/live
$ curl -fsS http://127.0.0.1:8787/health/ready
```

`live` 只证明 HTTP 事件循环能够响应，不能代表业务可用。`ready` 响应需要同时满足：

- `status=ready`；
- `database=ok`；
- `agents.codex` 与 `agents.claude` 均为 `available`；
- API 为 `configured`；
- `accepting_runs=true`；
- Telegram 未启用时为 `disabled`，启用时为 `running`。

上线前最小真实链路：

1. 分别用 codex/claude 运行只读 demo，确认登录态、JSON 事件解析和 session id。
2. 在一个可丢弃分支上运行无害 run，人工审阅 plan，再批准。
3. 检查工作区 diff、最终 result、usage 事件和 SQLite 持久化。
4. 运行一个可等待的任务并 stop，确认先出现 cancel requested，随后进入 cancelled；检查此前写入内容仍存在，以验证团队理解“停止不回滚”。
5. 通过真实 Telegram 账号完成自然语言问答、自然语言修改请求、按钮批准、Agent 切换和停止；只清理本轮测试会话或工作区变更，不清空共享数据库。

## 日志

日志输出为单行 JSON，包含 UTC timestamp、level、logger、message 和有限 extra 字段。异常只记录异常类型，不把完整 traceback 和潜在秘密发到 Telegram。脱敏是启发式的，日志平台仍需按敏感数据处理。

建议告警：

- ready 连续失败；
- `telegram polling conflict` 或持续 Bot API 错误；
- `run.failed`、`run.timed_out`、`run.interrupted` 比例突增；
- approval 大量 expired；
- 数据库 busy/磁盘空间不足；
- CLI malformed JSON warning，通常表示 CLI 协议版本漂移；
- CLI 凭据认证失败或额度错误。

日志不得包含 `.env` 内容、完整 Telegram URL、bearer token 或 CLI credential 文件。

## SQLite 备份与恢复

数据库使用 WAL。最安全的备份是在服务停止后复制数据库文件及存在的 `-wal`/`-shm`，或者使用 SQLite 在线 backup API。若主机安装 sqlite3，可在线生成一致快照：

```bash
$ sqlite3 /absolute/path/agent-relay.db ".backup '/secure/backup/agent-relay.db'"
$ chmod 600 /secure/backup/agent-relay.db
$ sqlite3 /secure/backup/agent-relay.db "PRAGMA integrity_check;"
```

备份包含 prompt、计划、结果、事件和远程身份，应加密并限制保留期。恢复步骤如下：

1. 停止服务。
2. 把现有数据库及 WAL 文件移到隔离目录。
3. 将通过完整性检查的快照复制到配置路径，并设置正确的 owner 和 `0600` 权限。
4. 启动服务并检查 ready。

不要在服务运行时只复制主 `.db` 文件，这可能漏掉 WAL 中已经提交的数据。

## 常见故障

### ready 返回 503，CLI missing

确认服务账号而不是交互账号的 PATH：

```bash
$ command -v codex
$ command -v claude
$ agent-relay doctor
```

launchd/systemd 不加载交互 shell rc。设置 `CODEX_EXECUTABLE` 和 `CLAUDE_EXECUTABLE` 为稳定绝对路径，或修正服务 PATH。相对 executable、PATH 中的相对项和全局可写项都会被拒绝/移除；不要用 shell wrapper 绕过 argv 安全模型。

doctor 报告 `unsafe path` 时，表示 CLI 本身、符号链接路径或真实目标路径的某一级目录允许任意本机用户写入。先用操作系统或包管理器推荐方式修正目录所有者和权限，再重新运行 doctor；不要在 Relay 中跳过这项检查，也不要为了消除告警而递归修改无关系统目录。

### CLI 可执行但认证失败

用服务相同的 OS 用户、HOME 和环境直接执行只读 CLI。macOS keychain 项可能只在登录会话可用；Linux 专用用户需要独立登录；Docker 必须使用容器可读取的专用 credential mounts。检查 `AGENT_ENV_ALLOWLIST` 是否错误移除了 CLI 必需变量，但不要一次性透传整个环境。

### Telegram 没有响应

依次检查 `TELEGRAM_ENABLED`、Bot token、chat/user 两份 allowlist、Bot 是否收到过私聊消息、主机到 `api.telegram.org` 的出站连接和 JSON 日志。被拒绝身份只写 warning，不向未授权聊天回消息。409 表示同一 token 有另一个 webhook/long-polling consumer；停止重复实例，不能横向扩展一个 token。

### Telegram 任务卡停止更新

先用 `/status` 回读数据库终态，再检查 watcher 日志。Telegram editMessage 的瞬时错误不会改变任务执行；HTTP GET/SSE 可作为独立真相来源。不要重复提交相同变更任务。

### approval 返回 409

重新 GET run。常见原因是审批已被处理、到期、任务已停止，或服务重启把任务标成 interrupted。审批接口不应盲目自动重试。

### stop 长时间停留在 cancel requested

runner 依次等待 SIGINT 和 SIGTERM grace，然后 SIGKILL。检查 CLI 是否产生主动脱离 process group 的后台进程，并从 OS 侧确认 PID。不要把第二次 stop 当作回滚；检查 workspace 和外部副作用。若服务本身被强杀，下次启动会把活跃 run 标为 interrupted。

### malformed JSON 或结果为空

记录 `codex --version`/`claude --version`，运行 adapter parser tests，并比较 CLI 官方 stream-json/exec-json 协议。Codex 没有 token delta，完成前只看到状态并非错误。输出达到 `SUBPROCESS_OUTPUT_LIMIT_BYTES` 时会产生 warning 并截断本地诊断；应缩小任务，而不是无限提高上限。

### database is locked

确认只有一个 Relay 进程写同一个数据库，磁盘不是不支持可靠锁的网络文件系统，目录可写且空间充足。SQLite 适用于单机守护进程，不适用于多个副本共享一个文件。需要横向扩展时应替换持久层与队列，而不是把 WAL 文件放进 NFS。

### 工作区被拒绝

路径必须存在且是目录，解析 symlink 后要位于至少一个 `WORKSPACE_ROOTS` 下。修改 allowlist 后重启服务。不要为了通过检查把 `/` 或整个 home 加入列表。

## 容量与保留

`events`、`runs` 和 `telegram_update_claims` 当前没有自动保留策略。运维侧需要：

- 监控数据库大小和磁盘空间，并按合规要求安排离线归档或清理；
- 在删除历史前完成备份，并使用经过审查的运维脚本；当前项目没有远程删除端点；
- 根据 CLI 额度、CPU、内存和 workspace 冲突设置 `MAX_CONCURRENT_RUNS`，不要简单提高到上限。
