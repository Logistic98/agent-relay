## 生产部署

## 选择部署方式

部署方式按 CLI 登录态、操作系统权限和隔离要求选择：

| 方式 | 适用场景 | 主要限制 |
| --- | --- | --- |
| 原生 launchd/systemd | 主部署路径；需要直接复用 CLI 官方登录态和 OS 沙箱 | 服务账号必须具备明确、最小的工作区权限 |
| Docker Compose | 两种 CLI 已在目标镜像和架构上完成实测，并需要额外容器边界 | 必须显式挂载单个 workspace 与必要凭据；不能透明复用 OS keychain |

所有部署方式都禁止 root 运行 Agent、挂载完整 home 或根目录，以及在权限失败时自动回退到危险模式。Mini App 的“完全访问”是用户主动选择的单次 run 策略，不是兼容性回退；生产环境可以继续通过外围网络和专用服务账号限制其能力。

## 通用安装

```bash
$ cd /absolute/path/to/agent-relay
$ uv sync --locked --all-groups
$ cp .env.example .env
$ chmod 600 .env
```

确认相同 OS 用户已经登录两种 CLI：

```bash
$ codex --version
$ claude --version
$ uv run agent-relay doctor
```

项目要求 Codex CLI >= 0.148.0、Claude Code >= 2.1.163。版本检查只是门禁的一部分；升级后还必须通过 doctor 和两种真实 demo 验证：

- CLI 路径安全；
- 登录状态报告；
- 事件协议解析；
- session 恢复。

不能只凭 `--version` 成功判断兼容。

编辑 `.env` 后先以前台方式启动并检查：

```bash
$ uv run agent-relay serve
$ curl -fsS http://127.0.0.1:8787/health/live
$ curl -fsS http://127.0.0.1:8787/health/ready
```

`live` 成功但 `ready` 返回 503 时不能视为业务可用。readiness 默认要求 Codex 和 Claude 两个 executable 都可发现。

## macOS LaunchAgent

使用当前开发者账号的 LaunchAgent，而不是 root LaunchDaemon。CLI 登录态和 workspace 权限必须属于这个账号。

1. 把仓库放在固定绝对路径，执行 `uv sync --locked --no-dev`，完成 `.env` 配置和 doctor。
2. 创建日志目录：

   ```bash
   $ mkdir -p "$HOME/Library/Logs/AgentRelay"
   $ chmod 700 "$HOME/Library/Logs/AgentRelay"
   ```

3. 复制 [plist 模板](../deploy/com.agent-relay.plist)，把以下占位符全部替换为绝对路径：

   - `__AGENT_RELAY_ROOT__`：仓库根目录。
   - `__AGENT_RELAY_HOME__`：运行账号 home，用于 CLI 登录态。
   - `__AGENT_RELAY_PATH__`：包含 `codex` 与 `claude` 的受控 PATH，例如 `/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin`。
   - `__AGENT_RELAY_LOG_DIR__`：上述日志目录。

   ```bash
   $ cp deploy/com.agent-relay.plist "$HOME/Library/LaunchAgents/com.agent-relay.plist"
   $ plutil -lint "$HOME/Library/LaunchAgents/com.agent-relay.plist"
   $ launchctl bootstrap "gui/$UID" "$HOME/Library/LaunchAgents/com.agent-relay.plist"
   $ launchctl enable "gui/$UID/com.agent-relay"
   $ launchctl kickstart -k "gui/$UID/com.agent-relay"
   ```

4. 查看状态和日志：

   ```bash
   $ launchctl print "gui/$UID/com.agent-relay"
   $ tail -f "$HOME/Library/Logs/AgentRelay/agent-relay.stdout.log"
   ```

卸载只停止服务，不删除数据库或 `.env`：

```bash
$ launchctl bootout "gui/$UID/com.agent-relay"
```

plist 的 WorkingDirectory 使 Pydantic 能读取仓库 `.env`。模板不把 token 写进 plist。若 CLI 由版本管理器安装，不要依赖交互 shell初始化；把 `CODEX_EXECUTABLE`、`CLAUDE_EXECUTABLE` 设置为稳定绝对路径，或显式配置最小 PATH。

## Linux systemd

推荐专用系统账号和单独目录：

```bash
$ sudo useradd --system --home-dir /var/lib/agent-relay --create-home --shell /usr/sbin/nologin agent-relay
$ sudo install -d -o agent-relay -g agent-relay -m 0700 /var/lib/agent-relay /var/lib/agent-relay/home
$ sudo install -d -o agent-relay -g agent-relay -m 0750 /srv/agent-workspaces
```

把代码安装到 `/opt/agent-relay`，创建只读虚拟环境，并让服务账号拥有需要写入的 workspace。Codex/Claude CLI 以及它们的登录态必须以 `agent-relay` 用户完成配置；不要复制个人账号的全部 home。示例流程需按各 CLI 官方登录方式执行：

```bash
$ cd /opt/agent-relay
$ sudo -u agent-relay uv sync --locked --no-dev
$ sudo install -o root -g agent-relay -m 0640 .env.example /etc/agent-relay.env
$ sudoedit /etc/agent-relay.env
$ sudo -u agent-relay env HOME=/var/lib/agent-relay/home /opt/agent-relay/.venv/bin/agent-relay doctor
```

复制并按实际 workspace 与 CLI 路径审阅 [systemd unit](../deploy/agent-relay.service)：

```bash
$ sudo install -o root -g root -m 0644 deploy/agent-relay.service /etc/systemd/system/agent-relay.service
$ sudo systemd-analyze verify /etc/systemd/system/agent-relay.service
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now agent-relay.service
$ systemctl status agent-relay.service
$ journalctl -u agent-relay.service -f
```

unit 使用 `ProtectSystem=strict`、专用 HOME、`ReadWritePaths`、最小地址族，并移除额外 capabilities。部署到不同 workspace 时必须显式修改 `ReadWritePaths`，不能删除整组 hardening。

如果 Codex 的 Linux sandbox 依赖当前内核缺失的能力，应升级内核或 CLI，或者改用受限容器；不要加入危险权限回退。

## 可选 Docker Compose

容器构建锁定 Python、Node、uv、Codex CLI 与 Claude Code CLI 的 ARG 默认版本，并以 `relay` 非 root 用户通过 `tini` 启动。Compose 具有只读根文件系统、drop all capabilities、no-new-privileges、PID 限制和 loopback 端口绑定。

准备专用 credential/session 目录和单个 workspace。Codex/Claude 原生 session 恢复通常需要写状态目录，因此这些 bind mount 是读写的；不要直接挂载整个 home。

```bash
$ cp .env.example .env
$ chmod 600 .env
$ mkdir -p /absolute/path/to/relay-data
$ docker compose config
$ docker compose build --pull
$ docker compose up -d
$ docker compose exec relay agent-relay doctor
$ curl -fsS http://127.0.0.1:8787/health/ready
```

必须在 `.env` 设置并确保存在：

- `AGENT_RELAY_WORKSPACE`：唯一的 host workspace，容器内固定为 `/workspace`。
- `CODEX_HOME_DIR`：专用 `.codex` 目录，挂载到 `/home/relay/.codex`。
- `CLAUDE_HOME_DIR`：专用 `.claude` 目录，挂载到 `/home/relay/.claude`。
- `CLAUDE_CONFIG_FILE`：专用 `.claude.json` 文件，挂载到 `/home/relay/.claude.json`。
- `AGENT_RELAY_DATA_DIR`：SQLite 持久目录。
- Telegram/API token 和两份 Telegram allowlist。

Linux bind mount 需要让 `RELAY_UID`/`RELAY_GID` 与 host 文件所有者匹配，默认值为 10001。macOS Docker Desktop 会执行 UID 映射，但仍需验证 CLI 能读取登录态并写入 session。

镜像不包含 token。Compose 配置值只从 `.env` 进入，凭据内容只来自显式 bind mount。

容器不是完全透明的原生替代，需要单独考虑以下差异：

- OS keychain 登录态不能直接复用；
- Docker 网络和文件通知行为可能不同；
- Codex/Claude 对 libc、CPU 架构和 sandbox 的支持可能随版本变化。

每次 CLI 版本升级后，应分别运行 Codex 和 Claude 的 ask demo，再执行一条人工批准的无害 run。构建失败或 sandbox 不兼容时，禁止改成 root、privileged、挂载 Docker socket、挂载 `/` 或添加危险权限参数。

## 反向代理与远程程序

首选 SSH 端口转发或私网 VPN，让 API 继续监听 loopback：

```bash
$ ssh -N -L 8787:127.0.0.1:8787 developer@workstation
```

如果必须用反向代理，代理应在同机访问 loopback，终止 TLS，执行强认证、请求大小限制和限流。Relay 自己的 bearer 仍需保留，`API_ACTOR_ID` 必须在服务端固定配置；不要信任客户端身份 header，也不要把 8787 直接发布到公网。

## 升级与回滚

升级前停止接收新任务，等待活跃任务终态或人工停止，随后离线备份 SQLite。更新代码后运行：

```bash
$ uv sync --locked --no-dev
$ uv run agent-relay doctor
$ uv run pytest
```

更新完成后重启服务，检查 ready，并执行一条真实 ask。

数据库 schema 当前通过 `CREATE TABLE IF NOT EXISTS` 初始化，没有版本化 downgrade 工具。初始化会为旧库中的活跃任务重建 workspace 租约；如果两个遗留任务的工作区存在祖先/后代重叠，服务会失败关闭，并要求先在备份副本中人工处理状态。

回滚代码前必须保留与旧版本兼容的数据库备份。运行期间直接替换代码或 CLI 会把任务标记为 `interrupted`，并且不会恢复执行。
