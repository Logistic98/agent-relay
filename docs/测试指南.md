## 测试与交付门禁

## 自动化门禁

本地和 CI 使用同一组命令：

```bash
$ uv lock --check
$ uv sync --locked --all-groups
$ uv run ruff check .
$ uv run ruff format --check .
$ uv run pytest
$ uv build
```

任何命令非零都表示门禁失败；`NO TESTS RAN` 不能视为成功。CI 不登录 Codex/Claude、不访问 Telegram、不读取开发者凭据。测试通过模拟 JSON 事件、临时 SQLite、fake HTTP transport 和受控 POSIX 子进程覆盖核心行为。

当前测试应至少覆盖：

- Codex/Claude argv 的只读与 execute 权限差异、session resume、事件解析、隐藏 thinking 不泄漏；
- Claude 文本 delta、Codex 完成消息、tool/usage/malformed event；
- 进程组正常完成、超时、SIGINT/SIGTERM/SIGKILL 取消和输出上限；
- SQLite WAL/schema、transport 所有权、单会话单活跃 run、跨会话及父子路径 workspace 租约、旧库租约回填、原子审批、事件序号、恢复 interrupted；
- workspace realpath allowlist、环境白名单和秘密脱敏；
- Telegram 命令解析、chat/user 双白名单、发起人审批、限流、API 重试/409；
- HTTP auth、owner 隔离、状态冲突和 SSE 回读；
- Telegram 卡片状态、审批说明、结果分片和停止不回滚提示。

## 配置与部署静态验证

```bash
$ plutil -lint deploy/com.agent-relay.plist
$ systemd-analyze verify deploy/agent-relay.service
$ AGENT_RELAY_ENV_FILE=.env.example docker compose --env-file .env.example config
```

前两条只在相应 OS/工具存在时执行。模板中的 launchd 路径占位符是合法字符串，所以 `plutil` 可检查 XML 结构；实际安装前仍必须全部替换。Compose config 必须保证 token 只来自 `.env`、端口只绑定 loopback、单 workspace/credential mounts 明确、没有 privileged/root/danger 参数。

## Doctor

```bash
$ uv run agent-relay doctor
```

doctor 用于部署前检查 Python 配置能否加载、database/workspace 路径、Codex/Claude executable 和关键安全配置。它还会拒绝位于非 sticky、全局可写目录中的 CLI，防止同机其他用户替换可执行文件。它不是 Agent 账户额度或完整网络链路的证明；CLI 能 `--version` 不等于能完成真实请求。

CLI `serve` 与直接 ASGI lifespan 都会强制执行相同门禁。自动化测试必须证明 doctor 失败时 Uvicorn 没有启动、直接 `main:app` 也启动失败，并验证相对 executable/PATH 不能因远程 cwd 改变而执行 workspace 内同名文件。

## 本地真实 demo

先用 ask 验证两种 Agent，不产生批准后的写操作：

```bash
$ uv run agent-relay demo --agent codex --workspace /absolute/path/to/test-project --mode ask --prompt "列出项目入口，不修改文件"
$ uv run agent-relay demo --agent claude --workspace /absolute/path/to/test-project --mode ask --prompt "列出测试命令，不修改文件"
```

再在干净、可丢弃的分支上验证 run：

```bash
$ uv run agent-relay demo --agent codex --workspace /absolute/path/to/test-project --mode run --prompt "在临时文档中追加一行并运行最小检查"
```

合格证据应同时包含：

- 只读 plan 在任何写入前完整显示，终端不会自动 approve；
- 拒绝后不启动 execute，批准后只启动一次 execute；
- 状态和工具事件可见，最终工作区 diff 与 plan 基本一致；
- 测试结果明确；
- stop 后检查工作区，并确认既有写入不会回滚。

## Transport 端到端

HTTP 验收按 README 的 curl 流程完成以下闭环：创建 conversation/run、订阅 SSE、执行 approve/reject/cancel，并通过 GET 回读终态。

Telegram 验收必须使用 allowlist 中的真实账号验证主页、项目选择、离开项目、会话切换、自然语言问答、修改请求、按钮审批、Agent 切换和停止；再用不在 allowlist 中的账号确认没有响应。测试不得自动批准真实 Agent 计划。

Mini App 验收按以下维度执行：

| 维度 | 验收内容 |
| --- | --- |
| 响应式布局 | 桌面常驻任务侧栏、手机任务抽屉、触控尺寸、固定输入框、软键盘避让和长回复下输入框可见 |
| 工作范围 | 底部工作范围选择器、新建无项目任务、项目搜索、项目进入与离开 |
| 会话与任务 | 会话切换、后台任务状态刷新、Agent 切换、停止、计划审批和连续消息持久排队 |
| 任务参数 | 模型、推理强度和三档权限选择；返回数据记录最终生效参数 |
| 过程可见性 | Agent 状态、工具开始/完成、命令摘要和增量输出；私有 reasoning 不进入页面或持久事件 |
| 文件预览 | 真实 PNG、文本/代码、PDF、音频、视频、普通二进制、下载和过大文件提示 |
| 文件安全 | `.env`、路径穿越和项目外符号链接均被拒绝 |
| 身份安全 | `full_access` 二次确认；缺少或伪造 Telegram `initData` 时 `/app/api/*` 返回 401 |

后台运行需要单独验证：启动一个阻塞任务，在运行期间切换到另一会话并离开项目，确认原 run 状态不变、适配器没有收到 cancel、侧栏继续刷新；切回原会话后应能看到最新输出，并正常停止或等待完成。

连续发送也需要单独验证：在前一任务未结束时再提交两条消息，确认后续消息保持 durable queued，并且只在前一条进入终态后开始。无项目状态必须能直接发送并创建通用会话，服务端必须把这类任务强制降为只读 ask 和默认审批权限。

## 版本升级矩阵

Python 依赖由 `uv.lock` 固定；Docker 的 Python/Node/uv/Codex/Claude 版本由 build ARG 默认值固定。升级任一 CLI 时至少完成：

1. adapter 单元测试；
2. `doctor`；
3. 两种 Agent 各一条真实 ask；
4. 对升级的 Agent 执行一条人工批准 run；
5. 取消与 session resume；
6. Telegram 和 HTTP 各一次事件展示检查。

若事件协议变化导致 malformed warning、session 丢失或权限语义不再成立，应阻止发布；不能用 root、危险权限或关闭 workspace 限制作为自动回退。完全访问模式只能来自任务发起人的明确选择。
